Actual specifications:
Each byte will contain a number from 0 to 127 (0x00 to 0x7F)
It is common for the data in the buffer to have the same value 
repeated in the series.
The compressed data will need to be decompressable.

Look at implementing simple compression algorithm that counts each repeated 
value in series, and adds a byte that describes the count and then the byte 
that that count corresponds to (run length encoding)

Ie: orig =  [1 1 1 1 4 4 4 3 3 3 4 3 3 3 3 9 9 9 8 9 0 0 0]

Would be [4 1 3 4 3 3 1 4 4 3 3 9 1 8 1 9 3 0]

This would compress from 23 to 18 bytes which is ~21.7% size reduction. This is a very ideal case though. Worst case is when all bytes have different values, or there aren't any in series, this would return a longer buffer.

Ie: [1 2 3 4 5 6 7 8]

Would be [1 1 1 2 1 3 1 4 1 5 1 6 1 7 1 8]

This worst case scenario doubles the buffer size which is not what we want.

If this is the case, and the buffer would be longer, would we have to measure that and just return back the original buffer so as not to add over the original allocated mem?

If we do this though, and then call for a decompression algorithm on it, it would be incorrect, so we would need a way to flag if it has been compressed or not. How do we assign a flag like that when we are given a buffer of size N and don't want to increase N. How could we flag a non-compressed buffer that we don't want to try and decompress?

I can look at adding a flag byte to the front of compressed code, that contains a number > 127 as that is the limit for buffer data. This would mean the check for if compression is worth it is if it compresses by > 1 byte. The compressed data minus the flag would have to be at least 2 lower to be worth compressing.
